# Riddim-specific project structures

Riddim shares the EP SysEx protocol and project format. This document covers
only its deltas: loop play mode, the `live` member, and the supertone synth.
**Firmware:** format bytes decoded on EP-40 OS 1.0.3 and verified identical on
OS 2.5.1; OS 2.5 added the USB audio used for the measurements.
Supertone knob semantics were measured by audio sweep on 2.5.1. The Identity
Reply returns zeroed version bytes on 2.5.x, so firmware is user-attested.

Shared format: [project-format.md](project-format.md) ·
protocol: [sysex-protocol.md](sysex-protocol.md) ·
open questions: [coverage.md](coverage.md).

## Device deltas at a glance

| | EP-133 K.O. II | EP-40 |
|---|---|---|
| SysEx product byte | `0x33` | **`0x3c`** — an EP-133-only client will not talk to an EP-40 |
| Pattern header | 4 bytes `[0, bars, count u8, 0]` | **6 bytes `[1, bars, 0xFF, 0xFF, count u16 LE]`** — every populated 2.5.1 capture (e.g. `[1,3,255,255,71,0]`, member length 6 + count×8); an earlier "4 bytes confirmed" claim here was wrong. Writing the 4-byte EP-133 form to an EP-40 is the leading suspect for the `err pattern 213` debug loop ([errors.md](errors.md#err-pattern-213)) |
| Time-signature scope | per-scene (scene chunk bytes 4–5) | unresolved; do not assume a different location |
| Play modes (pad byte 23) | 0 oneshot / 1 key / 2 legato | + **3 loop** |
| Extra persisted state | — | supertone synth params; `live` member (LSS) |
| Sample memory | 999 samples / 128 MB | same |

Project writes over `0x3c` are working (null/loop/supertone writes clean, no
debug frames) — but note **every one of those successful writes was
patternless** (byte-edits of native captures). Writes that introduce pattern
members must use the native 6-byte pattern header above.

## Loop play mode (pad record byte 23 = 3)

Verified on ~80 loop pads across all 8 factory jam projects. Loop mode adds
**no new pad-record fields** — it reuses the existing trim (bytes 4–11),
tempo-sync (`sound.bpm` f32 @12–15 with time-mode byte 21 = 1/bpm), and
mute-group (byte 22) fields. A loop pad plays its trimmed region as a
tempo-synced background layer; mute-group choke is the ordinary mechanism
applied to loops.

## `live` member — Loop Startup Sequence (LSS)

Projects **without populated patterns** carry a TAR member named **`live`** in
place of `fx_settings`; projects with patterns carry `fx_settings` and no
`live`. The two have not been observed to coexist — what happens for a
project with both loops *and* patterns is an open structural question.

- **48 bytes = 4 groups × 12 pads, one byte per pad**, in the usual A→D /
  p01→p12 order.
- Each byte is the pad's **armed/unmuted-by-default** state (0 or 1 observed) —
  the on-disk form of the officially documented Loop Startup Sequence: which
  loop pads trigger on the first beat when the project loads.
- Cross-validated against mute-group semantics: in a choked group exactly one
  loop pad is armed; in an unchoked group (mute-group 0) multiple may be
  armed. Non-loop pads are always 0.

**Write round-trip verified**: arming a different loop in a choked group
writes and reads back byte-exact, with no device-side normalization.

## Supertone synth pads

A supertone pad is an ordinary pad record pointing at a synth *symbol* instead
of a sample slot:

| Field | Pad-record bytes | Notes |
|---|---|---|
| engine | 1–2 (u16 LE) | stores **`sym − 1`**; metadata `sym` = 1001..1010 = supertone engines 0..9 |
| knobX | **27** (u8, 0–254) | = metadata `synth.params[0]` |
| knobY | **28** (u8, 0–254) | = metadata `synth.params[1]` |

Standard pad fields still apply (amp @16, root @24, playmode @23, pan @18,
attack @19, release @20, mute-group @22). **These two knobs are the complete
user-editable per-pad synth state** — per official TE docs, each supertone has
two preset parameters and the rest are engine-built-in. The 0–254 range is a
raw 8-bit knob position, **not** the 0..32767 fader/automation domain.
Supertone symbols have metadata but **no readable PCM** (FILE read fails with
"sample load failed") — the engines can only be captured from live audio.

Write round-trip verified (a single `synth.params` byte edit read back
byte-exact).

### Per-engine knob semantics (audio-sweep-measured, OS 2.5.1)

knobX resolved decisively for all 10 engines; knobY confirmed where it moves a
strong spectral feature, subtle otherwise. A community per-engine map was
independently confirmed; nothing contradicted it.

| sym | engine | knobX (byte 27) | knobY (byte 28) |
|---|---|---|---|
| 1001 | SU.0 | tone / brightness | age *(subtle)* |
| 1002 | SU.1 | **filter cutoff** | resonance |
| 1003 | SU.2 | **filter cutoff** | **unison** (amplitude beating/roughness +45% across the sweep — detuned stacked voices) |
| 1004 | SU.3 | **filter cutoff** | resonance / filter-env |
| 1005 | SU.4 | **filter cutoff** | PWM *(subtle)* |
| 1006 | SU.5 | tone / brightness | length / darken |
| 1007 | SU.6 | length / tone *(inverse: darkens)* | sweep *(subtle)* |
| 1008 | SU.7 dub siren (sine) | **tune / pitch** | speed *(LFO rate)* |
| 1009 | SU.8 dub siren (square) | **tune / pitch** | **speed** (LFO 1→14 Hz) |
| 1010 | SU.9 dub siren (saw) | **tune / pitch** | speed *(LFO rate)* |

Bold = strong, unambiguous spectral evidence. *(subtle)* = plausible per the
hypothesis but small movement at a single fixed note; quantifying would need
sustained-capture / detuning-beat metrics.

## Supertone automation in patterns

Populated supertone-group patterns interleave 8-byte automation records among
the note events, **identical in layout to the shared EP fader-automation record**
([project-format.md](project-format.md#fader-automation-record-8-bytes-interleaved)):

```text
pos u16 · 0x01 · paramID · 0x00 · value u16 (0..32767) · flag
```

Observed with **paramID = 0 (LVL)** — level automation on the supertone track
(dense volume gating, idiomatic for dub), not a bespoke supertone-motion
format. Values span 0 (mute) → ~32764 (full); confirmed by playing the
isolated supertone track over MIDI clock. **Open:** the trailing flag byte
takes `6/8/16` here vs `0` in the shared captures — candidate
curve/interpolation or continuation marker, undecoded.

## 1.0.3 → 2.5.1 serialization migration

**Activating** (not merely reading) a 1.0.3-authored project on 2.5.1
re-serializes it losslessly to the 2.5.1 form: previously-unassigned empty
pads are materialized (slot 0), and synth pads' unused `sample.start/end`
normalize from −1 to 0 (one project grew 62,976 → 64,000 B). **No musical
content changes** (settings/scenes/fx/patterns/pad-assignments
byte-identical). A pure read does not migrate. Never byte-diff a 1.0.3
capture against a 2.5.1 one — check member sizes first.
